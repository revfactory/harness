# Harness v2 — Agent Team & Skill Architect

도메인/프로젝트에 맞는 하네스를 구성하고, 각 에이전트의 역할을 정의하며, 에이전트가 사용할 스킬을 생성하는 메타 스킬.

**핵심 원칙:**
1. 에이전트 정의(`.claude/agents/`)와 스킬(`.claude/skills/`)을 생성한다. 에이전트는 "누가", 스킬은 "어떻게"를 담는다.
2. **실행 모드는 작업의 제어 흐름 형태로 결정한다.** — 결정적 제어 흐름은 워크플로우 오케스트레이션, 반복 협상·장기 협업은 퍼시스턴트 에이전트, 단발 위임은 서브에이전트. (Phase 2 참조)
3. **모델은 업무 특성으로 선택한다.** — 업무의 복잡도·작업 기간·자율성·응답 속도에 따라 opus(설계·코드 생성·복잡한 분석·교차 검증, 계획·장기 자율 실행) / sonnet(로그 파싱·포맷 변환·단순 수집 등 일상·기계적 업무)을 에이전트별로 선택한다. (Phase 3 모델 정책 참조)
4. **CLAUDE.md에 하네스 포인터를 등록한다.** — 새 세션에서 오케스트레이터 스킬이 트리거되도록 최소한의 포인터(트리거 규칙 + 변경 이력)만 기록한다.
5. **하네스는 고정물이 아니라 진화하는 시스템이다.** — 매 실행 후 피드백을 반영하고, 에이전트·스킬·CLAUDE.md를 지속 갱신한다. 회고와 델타 포착은 `harness:evolve` 스킬이 담당한다.

## 워크플로우

### Phase 0: 현황 감사

하네스 스킬이 트리거되면 가장 먼저 기존 하네스 현황을 확인한다.

1. `프로젝트/.claude/agents/`, `프로젝트/.claude/skills/`, `프로젝트/CLAUDE.md`를 읽는다
2. 현황에 따라 실행 모드를 분기한다:
   - **신규 구축**: 에이전트/스킬 디렉토리가 없거나 비어있음 → Phase 1부터 전체 실행
   - **기존 확장**: 기존 하네스가 있고 새 에이전트/스킬 추가 요청 → 아래 Phase 선택 매트릭스에 따라 필요한 Phase만 실행
   - **운영/유지보수**: 기존 하네스의 감사·수정·동기화 요청 → Phase 7 운영/유지보수 워크플로우로 이동

   **기존 확장 시 Phase 선택 매트릭스:**
   | 변경 유형 | Phase 1 | Phase 2 | Phase 3 | Phase 4 | Phase 5 | Phase 6 |
   |----------|---------|---------|---------|---------|---------|---------|
   | 에이전트 추가 | 건너뜀 (Phase 0 결과 활용) | 배치 결정만 | 필수 (3-0 포함) | 전용 스킬 필요 시 (4-0 포함) | 오케스트레이터 수정 | 필수 |
   | 스킬 추가/수정 | 건너뜀 | 건너뜀 | 건너뜀 | 필수 (4-0 포함) | 연결 변경 시 | 필수 |
   | 아키텍처/모드 변경 | 건너뜀 | 필수 | 영향받는 에이전트만 (3-0 포함) | 영향받는 스킬만 (4-0 포함) | 필수 | 필수 |
3. **v1 하네스 감지**: 기존 오케스트레이터에 `TeamCreate`/`TeamDelete`/`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` 참조가 있으면 v1 산출물이다. 현행 런타임에서 깨지므로 마이그레이션을 제안한다 (`references/execution-modes.md`의 "v1 → v2 마이그레이션" 참조).
4. 기존 에이전트/스킬 목록과 CLAUDE.md 기록을 대조하여 불일치(drift)를 감지한다
5. 감사 결과를 사용자에게 요약 보고하고, 실행 계획을 확인받는다

### Phase 1: 도메인 분석

1. 사용자 요청에서 도메인/프로젝트 파악
2. 핵심 작업 유형 식별 (생성, 검증, 편집, 분석 등)
3. **작업의 제어 흐름 형태 파악** — 실행 모드 선택의 근거가 된다:
   - 작업 목록이 사전에 열거 가능한가? (파일 N개 마이그레이션, 관점 M개 리뷰)
   - 산출물에 대한 검증/반복 루프가 필요한가?
   - 에이전트 간 실시간 협상·피드백 교환이 품질을 좌우하는가?
   - 세션을 넘나들며 같은 전문가와 계속 대화해야 하는가?
4. Phase 0 감사 결과를 기반으로 기존 에이전트/스킬과의 충돌/중복 분석
5. 프로젝트 코드베이스 탐색 — 기술 스택, 데이터 모델, 주요 모듈 파악
6. **사용자 숙련도 감지** — 대화의 맥락 단서(사용 용어, 질문 수준)로 기술 수준을 파악하고, 이후 커뮤니케이션 톤을 조절한다. 코딩 경험이 적은 사용자에게는 "assertion", "JSON schema" 같은 용어를 설명 없이 쓰지 않는다.

### Phase 2: 실행 모드 & 팀 아키텍처 설계

#### 2-1. 실행 모드 선택 (v2 3중 모드)

v2는 현행 Claude Code의 세 가지 멀티에이전트 프리미티브에 대응하는 3중 실행 모드를 제공한다. **모드는 작업의 제어 흐름 형태로 결정한다.**

| 모드 | 런타임 프리미티브 | 언제 사용 |
|------|------------------|----------|
| **워크플로우 오케스트레이션** | `Workflow` 스크립트 — `agent()` / `pipeline()` / `parallel()` / `phase()` | 제어 흐름이 **결정적**일 때: 팬아웃 목록이 사전 열거 가능, 검증 루프·반복 횟수가 코드로 표현 가능, 구조화된 산출물(스키마) 필요, 대규모(수십 개 이상) 에이전트 |
| **퍼시스턴트 에이전트 협업** | `Agent(name:)` + `SendMessage` + `TaskCreate`/`TaskUpdate` | 장기 전문가가 **컨텍스트를 유지**하며 반복 피드백·협상·공동 편집을 할 때. 세션에는 단일 암묵 팀이 있으며, 이름 붙인 에이전트는 SendMessage로 언제든 이어서 대화 가능 |
| **서브에이전트 위임** | `Agent` 단발 호출 (기본 백그라운드, 병렬 가능) | 단발성 위임으로 **결과만** 필요할 때. 통신·반복 불필요 |

**의사결정 순서:**
1. 작업 목록·검증 기준·반복 조건이 사전에 코드로 표현 가능한가? → **워크플로우**가 1순위. 결정적 제어 흐름을 모델 판단에 맡기지 않는 것이 재현성과 품질의 핵심이다.
2. 표현 불가능하고, 에이전트 간 실시간 협상·컨텍스트 유지가 품질을 좌우하는가? → **퍼시스턴트 에이전트**
3. 둘 다 아니고 결과 전달만 필요한가? → **서브에이전트**
4. Phase별 특성이 확연히 다르면 **하이브리드** — 각 Phase의 실행 모드를 오케스트레이터에 명시

**워크플로우 모드의 전제 조건:** `Workflow` 도구는 사용자의 명시적 옵트인이 필요하다. 하네스가 생성한 오케스트레이터 **스킬**의 지시문에 Workflow 호출이 명시되어 있으면, 사용자가 그 스킬을 트리거한 것 자체가 옵트인이다. 단, 오케스트레이터는 기본 규모를 절제하고(수 개 에이전트), 대규모 팬아웃은 사용자가 "철저히", "전수" 등을 요청했을 때만 확장한다.

> 상세 비교표, 각 프리미티브의 제약(동시성 캡, 스키마, 버짓, resume 등)은 `references/execution-modes.md` 참조.

#### 2-2. 아키텍처 패턴 선택

1. 작업을 전문 영역으로 분해
2. 팀 구조 결정 — 6가지 기본 패턴 (상세: `references/team-patterns.md`)
   - **파이프라인**: 순차 의존 작업 → 워크플로우 `pipeline()` 최적
   - **팬아웃/팬인**: 병렬 독립 작업 → 워크플로우 `parallel()`/`pipeline()` 최적
   - **전문가 풀**: 상황별 선택 호출 → 서브에이전트 또는 퍼시스턴트 전문가
   - **생성-검증**: 생성 후 품질 검수 → 워크플로우 적대적 검증 또는 퍼시스턴트 쌍
   - **감독자**: 중앙 조율 + 동적 분배 → 퍼시스턴트 에이전트 + 공유 태스크 목록
   - **계층적 위임**: 상위→하위 재귀 위임 → 2단계 이내, 워크플로우 중첩(1단계) 활용
3. **품질 패턴 검토** (v2 신규) — 산출물 품질이 중요한 하네스에는 워크플로우 네이티브 품질 패턴을 조합한다:
   - **적대적 검증**: 발견 하나당 N명의 반박자를 붙여 과반 반박 시 기각
   - **심판 패널**: N개 독립 시안 생성 → 병렬 심사 → 승자 기반 종합
   - **Loop-until-dry**: 신규 발견이 K라운드 연속 0이 될 때까지 탐색 반복
   - **다각 스윕**: 서로 다른 탐색 축(컨테이너별/내용별/개체별/시간별)의 병렬 조사
   - **완전성 비평가**: "무엇이 빠졌나"만 묻는 마지막 에이전트

#### 2-3. 에이전트 분리 기준

전문성·병렬성·컨텍스트·재사용성 4축으로 판단한다. 상세 기준표는 `references/team-patterns.md`의 "에이전트 분리 기준" 참조. 기존 에이전트와의 중복·재사용 검토는 Phase 3-0에서 다룬다.

### Phase 3: 에이전트 정의 생성

#### 3-0. 기존 에이전트 중복 검토

신규 에이전트 생성 전, `프로젝트/.claude/agents/`의 기존 에이전트와 중복 여부를 확인한다. 하네스를 반복 구축하다 보면 역할이 겹치는 에이전트가 다른 이름으로 누적되기 쉽다.

> 중복 분류 기준과 재사용 설계는 `references/team-patterns.md`의 "에이전트 분리 기준" 및 관련 설계 섹션 참조.

**모든 에이전트는 반드시 `프로젝트/.claude/agents/{name}.md` 파일로 정의한다.** 에이전트 정의 파일 없이 Agent 도구의 prompt에 역할을 직접 넣는 것은 금지한다. 이유:
- 파일로 존재해야 다음 세션에서 재사용 가능하고, `subagent_type: "{name}"`(Agent 도구) 및 `agentType: "{name}"`(Workflow)으로 호출 가능
- 통신 프로토콜이 명시되어야 에이전트 간 협업 품질 보장
- 하네스의 핵심 가치는 에이전트(누가)와 스킬(어떻게)의 분리

빌트인 타입(`general-purpose`, `Explore`, `Plan`)을 사용하더라도 에이전트 정의 파일은 생성한다. 빌트인 타입은 호출 시 타입 파라미터로 지정하고, 정의 파일에는 역할·원칙·프로토콜을 담는다.

**모델 정책 — 업무 특성 기반 선택:** 에이전트가 담당할 업무의 **복잡도·작업 기간·자율성·응답 속도** 4가지 기준으로 에이전트별 모델을 선택한다. 프론트매터 `model:` 또는 호출 파라미터(`model`/`opts.model`)로 지정하고, 선택 근거를 에이전트 정의 또는 오케스트레이터에 주석으로 남긴다.

| 모델 | 선택 기준 | 대표 업무 |
|------|----------|----------|
| **opus** | 깊은 추론·분석이 필요한 전문적·복잡한 문제, 또는 스스로 계획을 세워 여러 단계를 연결하는 장기·자율 실행 | 설계·아키텍처, 코드 생성(에이전트형 코딩), 복잡한 분석, 교차 검증·방법론 비판, 창작, 에이전트 오케스트레이션, 방대한 자료의 통합 |
| **sonnet** | 절차가 명확한 일상·기계적 업무. 속도-품질 균형 | 로그 파싱, 포맷 변환, 정적 파일 검사, 배포 스크립트 실행, 단순 수집, 일반 글쓰기·요약 |

판단 규칙:
- **opus vs sonnet**: 판단의 여지가 크거나 앞 단계의 결과가 다음 단계를 바꾸는 업무면 opus, 절차와 범위가 정해져 실행만 남은 업무면 sonnet. (예: 논문 심층 비판 / 논문 수십 편 검토 → 전략 → 보고서 → opus / 회의록을 정해진 양식으로 요약 → sonnet)
- **애매하면 sonnet**: 어떤 티어가 맞는지 확실하지 않은 일반 업무는 sonnet이 기본값이다.
- **일괄 지정 금지**: "전부 opus" 같은 무근거 일괄 지정은 금지. 티어는 에이전트의 중요도가 아니라 **업무의 성격**으로 판단한다.
- **계층 분리**: 계획·조율을 담당하는 오케스트레이션 계층에 opus를 두었다면, 그 아래 워커에는 각자의 업무 특성에 맞는 티어를 따로 적용한다.

> 티어별 상세 기준·적합 업무·선택 상황은 `references/model-selection-guide.md` 참조.

**에이전트 정의 프론트매터:** `name`, `description` 필수. 필요 시 `tools`(도구 제한 목록), `model`(오버라이드)을 추가한다. 읽기 전용이어야 하는 리뷰·분석 에이전트는 `tools`에서 Edit/Write를 제외하여 구조적으로 안전하게 만든다.

각 에이전트 정의의 필수 섹션: 핵심 역할, 작업 원칙, 입력/출력 프로토콜, 에러 핸들링, 협업. 퍼시스턴트 모드에서는 `## 통신 프로토콜` 섹션을 추가하여 SendMessage 수신/발신 대상과 공유 태스크 사용 규칙을 명시한다.

> 정의 템플릿과 실제 파일 전문은 `references/team-patterns.md`의 "에이전트 정의 구조" 참조.

**QA 에이전트 포함 시 필수 사항:**
- QA 에이전트는 도구 전체 접근이 가능한 타입을 사용하라 (`Explore`는 읽기 전용이라 검증 스크립트 실행 불가)
- QA의 핵심은 "존재 확인"이 아니라 **"경계면 교차 비교"** — API 응답과 프론트 훅을 동시에 읽고 shape을 비교
- QA는 전체 완성 후 1회가 아니라, **각 모듈 완성 직후 점진적으로 실행** (incremental QA)
- 상세 가이드: `references/qa-agent-guide.md` 참조

### Phase 4: 스킬 생성

각 에이전트가 사용할 스킬을 `프로젝트/.claude/skills/{name}/SKILL.md`에 생성한다. 상세 작성 가이드는 `references/skill-writing-guide.md` 참조.

#### 4-0. 기존 스킬 중복 검토

신규 스킬 생성 전, `프로젝트/.claude/skills/`의 기존 스킬과 중복 여부를 확인한다. 하네스를 반복 구축하다 보면 기능이 겹치는 스킬이 다른 이름으로 누적되기 쉽다.

> 중복 분류 기준과 일반화 패턴은 `references/skill-writing-guide.md`의 "스킬 재사용 설계" 참조.

#### 4-1. 스킬 구조

```
skill-name/
├── SKILL.md (필수)
│   ├── YAML frontmatter (name, description 필수)
│   └── Markdown 본문
└── Bundled Resources (선택)
    ├── scripts/    - 반복/결정적 작업용 실행 코드
    ├── references/ - 조건부 로딩하는 참조 문서
    └── assets/     - 출력에 사용되는 파일 (템플릿, 이미지 등)
```

#### 4-2. Description 작성 — 적극적 트리거 유도

description은 스킬의 유일한 트리거 메커니즘이다. Claude는 트리거를 보수적으로 판단하는 경향이 있으므로, description을 **적극적("pushy")**으로 작성한다.

**나쁜 예:** `"PDF 문서를 처리하는 스킬"`
**좋은 예:** `"PDF 파일 읽기, 텍스트/테이블 추출, 병합, 분할, 회전, 워터마크, 암호화, OCR 등 모든 PDF 작업을 수행. .pdf 파일을 언급하거나 PDF 산출물을 요청하면 반드시 이 스킬을 사용할 것."`

핵심: 스킬이 하는 일 + 구체적 트리거 상황을 모두 기술하고, 유사하지만 트리거하면 안 되는 경우와 구분되도록 작성.

#### 4-3. 본문 작성 원칙

| 원칙 | 설명 |
|------|------|
| **Why를 설명하라** | "ALWAYS/NEVER" 같은 강압적 지시 대신, 왜 그렇게 해야 하는지 이유를 전달한다. LLM은 이유를 이해하면 엣지 케이스에서도 올바르게 판단한다. |
| **Lean하게 유지** | 컨텍스트 윈도우는 공공재다. SKILL.md 본문은 500줄 이내를 목표로, 무게를 벌지 않는 내용은 삭제하거나 references/로 이동한다. |
| **일반화하라** | 특정 예시에만 맞는 좁은 규칙보다, 원리를 설명하여 다양한 입력에 대응할 수 있게 한다. 오버피팅 금지. |
| **반복 코드는 번들링** | 테스트 실행에서 에이전트들이 공통으로 작성하는 스크립트가 발견되면 `scripts/`에 미리 번들링한다. |
| **명령형으로 작성** | "~한다", "~하라" 형태의 명령형/지시형 어조를 사용한다. |

#### 4-4. Progressive Disclosure (단계적 정보 공개)

스킬은 3단계 로딩 시스템으로 컨텍스트를 관리한다:

| 단계 | 로딩 시점 | 크기 목표 |
|------|----------|----------|
| **Metadata** (name + description) | 항상 컨텍스트에 존재 | ~100단어 |
| **SKILL.md 본문** | 스킬 트리거 시 | <500줄 |
| **references/** | 필요할 때만 | 무제한 (스크립트는 로딩 없이 실행 가능) |

**크기 관리 규칙:**
- SKILL.md가 500줄에 근접하면 세부 내용을 references/로 분리하고, 본문에 "언제 이 파일을 읽으라"는 포인터를 남긴다
- 300줄 이상의 reference 파일에는 상단에 **목차(ToC)**를 포함한다
- 도메인/프레임워크별 변형이 있으면 references/ 하위에 도메인별로 분리하여, 관련 파일만 로드한다

#### 4-5. 스킬-에이전트 연결 원칙

- 에이전트 1개 ↔ 스킬 1~N개 (1:1 또는 1:다)
- 여러 에이전트가 공유하는 스킬도 가능
- 스킬은 "어떻게 하는가"를 담고, 에이전트는 "누가 하는가"를 담는다

### Phase 5: 통합 및 오케스트레이션

오케스트레이터는 스킬의 특수한 형태로, 개별 에이전트와 스킬을 하나의 워크플로우로 엮어 팀 전체를 조율한다. Phase 4의 개별 스킬이 "각 에이전트가 무엇을 어떻게 하는가"를 정의한다면, 오케스트레이터는 "누가 언제 어떤 순서로 협업하는가"를 정의한다. 모드별 템플릿 전문은 `references/orchestrator-template.md`, 워크플로우 스크립트 레시피는 `references/workflow-recipes.md` 참조.

**기존 확장 시:** 오케스트레이터를 새로 생성하지 않고 기존 것을 수정한다. 에이전트 추가 시 구성·작업 할당·데이터 흐름에 반영하고, description에 관련 트리거 키워드를 추가한다.

#### 5-0. 오케스트레이터 패턴 (모드별 요약)

**A. 워크플로우 오케스트레이션 (결정적 제어 흐름):**
오케스트레이터 스킬이 Workflow 스크립트를 정의한다. 스크립트는 `meta`(name/description/phases) + `pipeline()`/`parallel()`/`agent()` 본문으로 구성되며, 커스텀 에이전트는 `agentType`으로, 구조화 산출물은 `schema`로 받는다.

```
[오케스트레이터 스킬] → Workflow(script)
    ├── phase('수집'): pipeline(items, ...)   ← 결정적 팬아웃
    ├── phase('검증'): 적대적 검증 / 심판 패널
    └── return 구조화 결과 → 메인이 종합 보고
```

**B. 퍼시스턴트 에이전트 협업 (반복 협상·장기 협업):**
이름 붙인 에이전트들을 스폰하고, 공유 태스크 목록과 SendMessage로 조율한다. TeamCreate/TeamDelete는 존재하지 않는다 — 세션에 단일 암묵 팀이 있고, `Agent(name: "...")`으로 스폰한 에이전트는 SendMessage로 컨텍스트를 유지한 채 계속 대화할 수 있다.

```
[메인/리더]
    ├── Agent(name: "researcher", ...) / Agent(name: "critic", ...)  ← 병렬 스폰
    ├── TaskCreate(작업 + 의존성)
    ├── SendMessage({to: "critic"}, "researcher의 초안을 검토하라")   ← 반복 조율
    └── 결과 수집 및 종합
```

**C. 서브에이전트 위임 (단발 병렬):**
단일 메시지에서 N개 Agent를 병렬 호출(기본 백그라운드)하고, 완료 알림을 받아 결과를 수집한다.

**하이브리드:** Phase마다 모드를 섞는다. 자주 쓰는 조합: 워크플로우 수집 → 퍼시스턴트 합의 통합, 퍼시스턴트 생성 → 워크플로우 적대적 검증. 각 Phase 상단에 `**실행 모드:**`를 명시한다.

#### 5-1. 데이터 전달 프로토콜

| 전략 | 방식 | 적용 모드 | 적합한 경우 |
|------|------|----------|-----------|
| **구조화 반환** | Workflow `agent(prompt, {schema})` — 검증된 JSON 반환 | 워크플로우 | 산출물을 후속 단계가 프로그래밍으로 소비 (v2 권장 기본) |
| **반환값 기반** | Agent 도구의 반환 메시지 | 서브 | 요약 결과를 메인이 직접 수집 |
| **메시지 기반** | `SendMessage`로 에이전트 간 직접 통신 | 퍼시스턴트 | 실시간 조율, 피드백 교환 |
| **태스크 기반** | `TaskCreate`/`TaskUpdate`로 작업 상태 공유 | 퍼시스턴트 | 진행 추적, 의존 관계, 동적 할당 |
| **파일 기반** | 약속된 경로에 파일을 쓰고 읽음 | 전체 | 대용량 데이터, 감사 추적 필요 |

파일 기반 전달 시 규칙:
- 작업 디렉토리 하위에 `_workspace/` 폴더를 만들어 중간 산출물 저장
- 파일명 컨벤션: `{phase}_{agent}_{artifact}.{ext}` (예: `01_analyst_requirements.md`)
- 최종 산출물만 사용자 지정 경로에 출력, 중간 파일(`_workspace/`)은 보존 (사후 검증·감사 추적용)

#### 5-2. 에러 핸들링

오케스트레이터 내에 에러 처리 방침을 포함한다. 핵심 원칙:
- 1회 재시도 후 재실패 시 해당 결과 없이 진행하되 보고서에 누락 명시. 상충 데이터는 삭제하지 않고 출처 병기
- **워크플로우 모드**: 실패/스킵된 `agent()`는 `null`을 반환하고 `parallel()`은 절대 reject되지 않는다 — 결과 배열에 반드시 `.filter(Boolean)`을 적용하고, 드랍된 항목 수를 `log()`로 알린다 (침묵 누락 금지)
- **퍼시스턴트 모드**: 무응답 에이전트는 SendMessage로 상태 확인 → 재지시 → 실패 시 새 에이전트로 대체

> 에러 유형별 전략표는 `references/orchestrator-template.md`의 "에러 핸들링" 참조.

#### 5-3. 규모 가이드라인

| 작업 규모 | 퍼시스턴트 팀원 수 | 워크플로우 동시 에이전트 |
|----------|-----------------|----------------------|
| 소규모 (5~10개 작업) | 2~3명 | 수 개 |
| 중규모 (10~20개 작업) | 3~5명 | ~10개 (동시성 캡 내 자동 큐잉) |
| 대규모 (20개+ 작업) | 감독자 + 워커 3~5명 | 수십~수백 개 (총량 캡 1000) |

- 팀원이 많을수록 조율 오버헤드가 커진다. 3명의 집중된 팀원이 5명의 산만한 팀원보다 낫다.
- 사용자가 토큰 버짓 지시("+500k")를 준 세션에서는 워크플로우 스크립트에서 `budget.remaining()`으로 규모를 동적으로 조절한다.

#### 5-4. CLAUDE.md 하네스 포인터 등록

하네스 구성 완료 후, 프로젝트의 `CLAUDE.md`에 최소한의 포인터를 등록한다. CLAUDE.md는 새 세션마다 로딩되므로, 하네스 존재와 트리거 규칙만 기록하면 오케스트레이터 스킬이 나머지를 처리한다.

**CLAUDE.md 템플릿:**

````markdown
## 하네스: {도메인명}

**목표:** {하네스의 핵심 목표 한 줄}

**트리거:** {도메인} 관련 작업 요청 시 `{orchestrator-skill-name}` 스킬을 사용하라. 단순 질문은 직접 응답 가능.

**변경 이력:**
| 날짜 | 변경 내용 | 대상 | 사유 |
|------|----------|------|------|
| {YYYY-MM-DD} | 초기 구성 (harness v2) | 전체 | - |
````

**CLAUDE.md에 넣지 않는 것:** 에이전트 목록, 스킬 목록, 디렉토리 구조, 실행 규칙 상세. 이유: 에이전트/스킬 목록은 오케스트레이터 스킬과 `.claude/agents/`, `.claude/skills/`에서 단일 출처로 관리하므로 중복이다. CLAUDE.md는 **포인터(트리거 규칙) + 변경 이력**만 담는다.

#### 5-5. 후속 작업 지원

오케스트레이터는 초기 실행뿐 아니라 후속 작업도 처리해야 한다. 다음 세 가지를 보장하라:

**1. 오케스트레이터 description에 후속 키워드 포함:**
- "다시 실행", "재실행", "업데이트", "수정", "보완"
- "{도메인}의 {부분작업}만 다시"
- "이전 결과 기반으로", "결과 개선"

후속 키워드가 없으면 첫 실행 후 하네스가 사실상 죽은 코드가 된다.

**2. 오케스트레이터 Phase 0에 컨텍스트 확인 단계:**
- `_workspace/` 존재 + 부분 수정 요청 → **부분 재실행** (해당 단계/에이전트만)
- `_workspace/` 존재 + 새 입력 제공 → **새 실행** (기존 `_workspace/`를 타임스탬프 디렉토리로 이동)
- `_workspace/` 미존재 → **초기 실행**
- **워크플로우 모드 추가 옵션**: 직전 실행의 `runId`가 있으면 `resumeFromRunId`로 재개 — 변경되지 않은 `agent()` 호출은 캐시에서 즉시 반환되므로 부분 재실행이 매우 저렴하다

**3. 에이전트 정의에 재호출 지침 포함:**
- 이전 결과 파일이 존재하면 읽고 개선점을 반영
- 사용자 피드백이 주어지면 해당 부분만 수정

### Phase 6: 검증 및 테스트

생성된 하네스를 검증한다. 상세 테스트 방법론은 `references/skill-testing-guide.md` 참조.

#### 6-1. 구조 검증

- 모든 에이전트 파일이 올바른 위치에 있는지 확인
- 스킬의 frontmatter(name, description) 검증
- 에이전트 간 참조 일관성 확인
- 커맨드(`.claude/commands/`)가 생성되지 않았는지 확인
- **v1 잔재 검증**: 산출물에 `TeamCreate`/`TeamDelete`/`team_name`/실험 플래그 참조가 없는지 확인

#### 6-2. 실행 모드별 검증

- **워크플로우**: 스크립트의 `meta`가 순수 리터럴인지, `Date.now()`/`Math.random()` 미사용인지, 배리어(`parallel`)가 정말 필요한 곳에만 있는지, `.filter(Boolean)` 누락이 없는지, phase 제목이 meta.phases와 일치하는지
- **퍼시스턴트**: SendMessage 수신/발신 경로, 태스크 의존성, 팀 크기 적정성
- **서브에이전트**: 각 에이전트의 입출력 연결, 병렬 호출이 단일 메시지에 묶였는지, 결과 수집 로직
- **하이브리드**: 각 Phase의 실행 모드가 명시되었는지, Phase 경계에서 데이터 전달이 끊기지 않는지

#### 6-3. 스킬 실행 테스트

생성된 각 스킬에 대해 실제 실행 테스트를 수행한다:

1. **테스트 프롬프트 작성** — 스킬당 2~3개의 현실적인 프롬프트. 실제 사용자가 입력할 법한 구체적이고 자연스러운 문장으로.
2. **With-skill vs Without-skill 비교 실행** — 스킬 있는 실행과 없는 실행을 병렬 수행하여 부가가치를 확인한다. 반복 검증이 필요하면 이 비교 자체를 워크플로우 스크립트로 구성할 수 있다 (`references/skill-testing-guide.md`의 "워크플로우 기반 A/B" 참조).
3. **결과 평가** — 정성적(사용자 리뷰) + 정량적(assertion 기반). 객관 검증 가능하면 assertion을 정의하고, 주관적이면 사용자 피드백에 의존한다.
4. **반복 개선 루프** — 문제 발견 시 피드백을 **일반화**하여 수정 → 재테스트 → 만족 또는 수확 체감까지 반복.
5. **반복 패턴 번들링** — 테스트에서 에이전트들이 공통으로 작성하는 코드가 발견되면 `scripts/`에 번들링한다.

#### 6-4. 트리거 검증

1. **Should-trigger 쿼리** (8~10개) — 다양한 표현 (공식적/캐주얼, 명시적/암시적)
2. **Should-NOT-trigger 쿼리** (8~10개) — 키워드가 유사하지만 다른 도구/스킬이 적합한 "near-miss" 쿼리

**near-miss 작성 핵심:** "피보나치 함수 작성" 같이 명백히 무관한 쿼리는 테스트 가치가 없다. "이 엑셀 파일의 차트를 PNG로 추출해줘" (xlsx 스킬 vs 이미지 변환)처럼 **경계가 모호한 쿼리**가 좋은 테스트 케이스다.

기존 스킬과의 트리거 충돌도 이 단계에서 확인한다.

#### 6-5. 드라이런 테스트

- 오케스트레이터 Phase 순서가 논리적인지 검토
- 데이터 전달 경로에 빈 구간(dead link)이 없는지 확인
- 모든 에이전트의 입력이 이전 Phase의 출력과 매칭되는지 확인
- 에러 시나리오별 폴백 경로가 실행 가능한지 확인

#### 6-6. 테스트 시나리오 작성

- 오케스트레이터 스킬에 `## 테스트 시나리오` 섹션 추가 — 정상 흐름 1개 + 에러 흐름 1개 이상

### Phase 7: 운영/유지보수 & 진화

하네스는 한 번 만들고 끝나는 정적 산출물이 아니다.

**실행 후 피드백과 회고·델타 포착은 `harness:evolve` 스킬이 전담한다.** 사용자가 "하네스 회고", "하네스 진화", "피드백 반영해줘"라고 하면 evolve 스킬로 안내한다. evolve는 초기 구성과 현재 상태의 델타를 분석하고, 피드백을 일반화하여 에이전트·스킬·오케스트레이터에 반영하며, CLAUDE.md 변경 이력을 갱신한다.

이 스킬(harness)이 직접 처리하는 것은 **운영/유지보수 워크플로우**다 (Phase 0에서 "운영/유지보수" 분기로 진입 시):

**Step 1: 현황 감사** — `.claude/agents/`·`.claude/skills/` 목록과 오케스트레이터 구성을 비교 → 불일치 목록 생성 → 사용자에게 보고
**Step 2: 점진적 추가/수정** — 변경은 한 번에 하나씩, 각 변경 후 즉시 Step 3 실행
**Step 3: CLAUDE.md 변경 이력 갱신** — 날짜, 변경 내용, 대상, 사유 기록
**Step 4: 변경 검증** — 구조 검증(6-1), 트리거 영향 시 트리거 검증(6-4), 대규모 변경 시 실행 테스트(6-3)·드라이런(6-5)까지. CLAUDE.md와 실제 파일의 일치 여부 최종 확인

**선제적 진화 제안 트리거:**
- 같은 유형의 피드백이 2회 이상 반복될 때
- 에이전트가 반복적으로 실패하는 패턴이 발견될 때
- 사용자가 오케스트레이터를 우회하여 수동으로 작업하는 것이 관찰될 때

## 산출물 체크리스트

생성 완료 후 확인:

- [ ] `프로젝트/.claude/agents/` — **에이전트 정의 파일 필수 생성** (빌트인 타입이라도 파일 생성 필수)
- [ ] `프로젝트/.claude/skills/` — 스킬 파일들 (SKILL.md + references/)
- [ ] 오케스트레이터 스킬 1개 (데이터 흐름 + 에러 핸들링 + 테스트 시나리오 포함)
- [ ] 실행 모드 명시 (워크플로우 / 퍼시스턴트 / 서브에이전트 / 하이브리드, 하이브리드면 Phase별 모드 기재)
- [ ] 모델 선택 — 에이전트별 `model:`이 업무 특성(복잡도·작업 기간·자율성·응답 속도) 기준으로 선택되고 근거가 주석으로 남음. "전부 opus" 같은 무근거 일괄 지정 없음
- [ ] 신규 에이전트 생성 전 기존 에이전트 중복 검토 완료 (Phase 3-0)
- [ ] 신규 스킬 생성 전 기존 스킬 중복 검토 완료 (Phase 4-0)
- [ ] 산출물에 `TeamCreate`/`TeamDelete`/실험 플래그 참조 없음 (v1 잔재 금지)
- [ ] 워크플로우 스크립트에 `.filter(Boolean)`·순수 리터럴 `meta`·배리어 최소화 적용
- [ ] `.claude/commands/` — 아무것도 생성하지 않음
- [ ] 기존 에이전트/스킬과 충돌 없음
- [ ] 스킬 description이 적극적("pushy")으로 작성됨 — **후속 작업 키워드 포함**
- [ ] SKILL.md 본문이 500줄 이내, 초과 시 references/ 분리
- [ ] 테스트 프롬프트 2~3개로 실행 검증 완료
- [ ] 트리거 검증 (should-trigger + should-NOT-trigger) 완료
- [ ] **CLAUDE.md에 하네스 포인터 등록** (트리거 규칙 + 변경 이력)
- [ ] **오케스트레이터 Phase 0에 컨텍스트 확인 단계** (초기/후속/부분 재실행 판별, 워크플로우면 resume 옵션)
