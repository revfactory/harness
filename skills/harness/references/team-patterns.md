## 1. 기본 패턴 6종

### 1-1. 파이프라인 (Pipeline)

순차적 작업 흐름. 이전 에이전트의 출력이 다음 에이전트의 입력.

```
[분석] → [설계] → [구현] → [검증]
```

**적합:** 각 단계가 이전 단계의 산출물에 강하게 의존
**예시:** 소설 집필 — 세계관 → 캐릭터 → 플롯 → 집필 → 편집
**주의:** 병목이 전체를 지연시킴. 각 단계를 가능한 독립적으로 설계할 것.
**v2 권장 모드:** 단계와 항목이 사전 열거 가능하면 **워크플로우 `pipeline()`** — 항목별로 단계 간 배리어 없이 흐르므로 벽시계 시간이 최소화된다. 단계 산출물에 대한 인간 검토가 사이에 끼면 서브에이전트 순차 호출.

### 1-2. 팬아웃/팬인 (Fan-out/Fan-in)

병렬 처리 후 결과 통합. 독립적 작업을 동시 수행.

```
         ┌→ [전문가A] ─┐
[분배] → ├→ [전문가B] ─┼→ [통합]
         └→ [전문가C] ─┘
```

**적합:** 동일 입력에 대해 서로 다른 관점/영역의 분석이 필요
**예시:** 종합 리서치 — 공식/미디어/커뮤니티/배경 동시 조사 → 통합 보고
**주의:** 통합 단계의 품질이 전체 품질을 결정.
**v2 권장 모드:** **워크플로우**가 1순위 — 관점 목록을 배열로 정의하고 `pipeline()`으로 흘리며, `schema`로 구조화 수집 후 코드로 병합한다. 통합 전에 전체 결과의 dedup이 필요할 때만 `parallel()` 배리어. 조사자 간 실시간 발견 공유가 품질을 좌우하는 소규모(2~4명) 리서치는 퍼시스턴트 모드도 유효.

### 1-3. 전문가 풀 (Expert Pool)

상황에 따라 적절한 전문가를 선택 호출.

```
[라우터] → { 전문가A | 전문가B | 전문가C }
```

**적합:** 입력 유형에 따라 다른 처리가 필요
**예시:** 코드 리뷰 — 보안/성능/아키텍처 전문가 중 해당 영역만 호출
**주의:** 라우터의 분류 정확도가 핵심.
**v2 권장 모드:** **서브에이전트** — 필요한 전문가만 단발 호출. 전문가와의 후속 대화가 이어지면 `name`을 붙여 퍼시스턴트로 승격.

### 1-4. 생성-검증 (Producer-Reviewer)

생성 에이전트와 검증 에이전트가 쌍으로 동작.

```
[생성] → [검증] → (문제시) → [생성] 재실행
```

**적합:** 품질 보장이 중요하고 객관적 검증 기준이 존재
**주의:** 무한 루프 방지를 위해 최대 재시도 횟수(2~3회) 설정 필수.
**v2 권장 모드:** 검증 기준이 코드로 표현 가능하면 **워크플로우** — 적대적 검증 패턴(아래 2-1)으로 발견별 병렬 검증. 검증이 주관적이고 협상이 필요하면 **퍼시스턴트 쌍** — 생성자와 검증자를 이름 붙여 스폰하고 SendMessage로 피드백 루프 (생성자가 컨텍스트를 유지하므로 재작업이 정확하다).

### 1-5. 감독자 (Supervisor)

중앙 에이전트가 작업 상태를 관리하며 동적으로 작업을 분배.

```
         ┌→ [워커A]
[감독자] ─┼→ [워커B]    ← 진행 상황을 보고 동적 분배
         └→ [워커C]
```

**적합:** 작업량이 가변적이거나 런타임에 분배를 결정해야 할 때
**팬아웃과의 차이:** 팬아웃은 사전 고정 분배, 감독자는 진행 상황 기반 동적 조정
**주의:** 감독자가 병목이 되지 않도록 위임 단위를 충분히 크게.
**v2 권장 모드:** **퍼시스턴트** — 리더(메인)가 `TaskCreate`로 작업을 등록하고, 워커 완료 알림을 받아 `SendMessage`/`TaskUpdate`로 재분배. 작업 목록이 사전 확정되고 분배 로직이 코드로 표현 가능해지는 순간 워크플로우로 전환하는 편이 낫다 (감독자 판단 자체가 결정적이면 감독자는 불필요).

### 1-6. 계층적 위임 (Hierarchical Delegation)

상위 에이전트가 하위에 재귀적으로 위임. 복잡한 문제를 단계적으로 분해.

```
[총괄] → [팀장A] → [실무자A1, A2]
       → [팀장B] → [실무자B1]
```

**적합:** 문제가 자연스럽게 계층적으로 분해되는 구조
**주의:** 깊이 3단계 이상은 지연과 컨텍스트 손실이 커짐. **2단계 이내 권장.**
**v2 권장 모드:** **워크플로우 중첩** — 상위 워크플로우가 `workflow(nameOrRef, args)`로 하위 워크플로우를 호출 (중첩은 1단계만 지원되며, 이 제약이 과도한 계층화를 구조적으로 막아준다). 또는 평탄화하여 단일 워크플로우의 phase로 재구성.

## 2. 품질 패턴 (v2 신규)

산출물 품질이 중요한 하네스에 조합하는 워크플로우 네이티브 패턴. 그럴듯하지만 틀린 결과(plausible-but-wrong)를 걸러내는 것이 목적이다.

| 패턴 | 구조 | 언제 |
|------|------|------|
| **적대적 검증** | 발견 1건당 N명의 독립 반박자(refuter) 스폰 → 과반 반박 시 기각 | 발견/주장의 신뢰도가 중요할 때 (리뷰, 감사, 리서치) |
| **관점 분산 검증** | 반박자 N명에게 동일 프롬프트 대신 서로 다른 렌즈(정확성/보안/재현성)를 부여 | 실패 모드가 여러 방향일 때 — 다양성이 중복보다 많이 잡는다 |
| **심판 패널** | N개 독립 시안(서로 다른 각도) → 병렬 심사 → 승자 기반 + 차점자의 장점 접목 종합 | 해공간이 넓은 설계/기획 (한 시안을 반복 개선하는 것보다 우월) |
| **Loop-until-dry** | 신규 발견이 K라운드 연속 0이 될 때까지 탐색 반복. 기각된 발견도 `seen`에 남겨 재등장 방지 | 크기를 모르는 발견 작업 (버그, 이슈, 엣지 케이스) — 고정 횟수 루프는 꼬리를 놓친다 |
| **다각 스윕** | 서로 다른 탐색 축(컨테이너별/내용별/개체별/시간별)의 병렬 에이전트 | 한 가지 탐색 방식으로 전부 찾을 수 없을 때 |
| **완전성 비평가** | 마지막에 "빠진 것은 무엇인가 — 안 돌린 축, 미검증 주장, 안 읽은 소스?"만 묻는 에이전트 1명 | 종합 단계 직전. 발견이 다음 라운드 작업이 된다 |
| **침묵 상한 금지** | top-N, 샘플링 등으로 커버리지를 제한하면 드랍된 양을 반드시 `log()` | 모든 팬아웃 — 침묵 절단은 "전부 봤다"로 오독된다 |

**규모 조정 원칙:** 사용자 요청 강도에 비례한다. "버그 있나 봐줘" → 소수 탐색자 + 단일 검증. "철저히 감사해줘" → 대형 탐색 풀 + 3~5표 적대적 검증 + 종합 단계. 확신이 없으면 리서치/리뷰/감사류는 철저한 쪽으로, 빠른 확인류는 간결한 쪽으로.

> 구현 스켈레톤은 `workflow-recipes.md` 참조.

## 3. 복합 패턴

실전에서는 단일 패턴보다 복합 패턴이 흔하다:

| 복합 패턴 | 구성 | 예시 |
|----------|------|------|
| **팬아웃 + 생성-검증** | 병렬 생성 후 각각 검증 | 다국어 번역 — 4개 언어 병렬 번역 → 각각 네이티브 리뷰어 검수 |
| **파이프라인 + 팬아웃** | 순차 단계 중 일부를 병렬화 | 분석(순차) → 구현(병렬) → 통합 테스트(순차) |
| **감독자 + 전문가 풀** | 감독자가 전문가를 동적 호출 | 고객 문의 처리 — 감독자가 분류 후 적합한 전문가 할당 |
| **탐색 + 적대적 검증 + 종합** | 다각 스윕 → 발견별 검증 → 비평가 → 보고 | 종합 코드 감사, 딥 리서치 |

복합 패턴에서 모드는 Phase 단위로 선택한다 (하이브리드). 각 Phase의 제어 흐름이 결정적인지 여부가 기준이다.

## 4. 에이전트 타입 선택

에이전트를 호출할 때 Agent 도구의 `subagent_type`(또는 Workflow의 `agentType`) 파라미터로 타입을 지정한다.

### 빌트인 타입

| 타입 | 도구 접근 | 적합한 용도 |
|------|----------|-----------|
| `general-purpose` | 전체 (WebSearch, WebFetch 포함) | 웹 조사, 범용 작업, 파일 수정 |
| `Explore` | 읽기 전용 (Edit/Write 없음) | 코드베이스 탐색 — 코드의 위치를 찾는 용도. 리뷰·감사가 아니다 |
| `Plan` | 읽기 전용 (Edit/Write 없음) | 아키텍처 설계, 구현 계획 수립 |

### 커스텀 타입

`.claude/agents/{name}.md`에 정의하면 `subagent_type: "{name}"` / `agentType: "{name}"`으로 호출할 수 있다. 프론트매터로 도구·모델을 제어한다.

### 선택 기준

| 상황 | 권장 | 이유 |
|------|------|------|
| 역할이 복잡하고 여러 세션에서 재사용 | **커스텀 타입** | 페르소나와 작업 원칙을 파일로 관리 |
| 단순 조사/수집이고 프롬프트만으로 충분 | `general-purpose` + 상세 프롬프트 | 단, 에이전트 정의 파일은 그래도 생성 (재사용성) |
| 코드 위치 탐색만 필요 | `Explore` | 실수로 파일을 수정하는 것을 구조적으로 방지 |
| 설계/계획만 필요 | `Plan` | 분석에 집중, 코드 변경 방지 |
| 파일 수정이 필요한 구현 작업 | **커스텀 타입** | 전체 도구 접근 + 전문 지시 |
| 병렬 파일 수정 작업 | 커스텀 + `isolation: 'worktree'` | 에이전트끼리 같은 파일을 건드리는 충돌 방지 (셋업 비용이 있으므로 병렬 변경 시에만) |

**원칙:** 모든 에이전트는 반드시 `.claude/agents/{name}.md` 파일로 정의한다. 빌트인 타입이라도 정의 파일을 생성하여 역할·원칙·프로토콜을 명시한다.

**모델 정책:** 업무의 복잡도·작업 기간·자율성·응답 속도로 티어를 선택한다 — **opus**(설계·아키텍처, 코드 생성, 복잡한 분석, 교차 검증, 창작, 계획 수립·장기 자율 실행, 에이전트 오케스트레이션), **sonnet**(로그 파싱·포맷 변환·정적 파일 검사·배포 스크립트 실행·단순 수집 등 일상·기계적 업무). 애매하면 sonnet, 무근거 일괄 지정 금지, 선택 이유는 주석으로 남긴다. 상세: `model-selection-guide.md`.

## 5. 에이전트 정의 구조

```markdown
---
name: agent-name
description: "1-2문장 역할 설명. 트리거 키워드 나열."
# tools: Read, Grep, Glob, Bash        ← 선택: 도구 제한 (읽기 전용 리뷰어 등)
# model: sonnet                         ← 업무 특성 기반 선택 (model-selection-guide.md), 이유를 주석으로
---

# Agent Name — 역할 한줄 요약

당신은 [도메인]의 [역할] 전문가입니다.

## 핵심 역할
1. 역할1
2. 역할2

## 작업 원칙
- 원칙1 (Why 포함 — 이유를 알면 엣지 케이스에서도 올바르게 판단한다)
- 원칙2

## 입력/출력 프로토콜
- 입력: [어디서 무엇을 받는지 — 파일 경로, args, 이전 단계 산출물]
- 출력: [어디에 무엇을 쓰는지 — _workspace/ 경로 또는 구조화 반환]
- 형식: [파일 포맷, 구조, 스키마]

## 통신 프로토콜 (퍼시스턴트 모드)
- 메시지 수신: [누구로부터 어떤 메시지를 받는지]
- 메시지 발신: [누구에게 어떤 메시지를 보내는지]
- 공유 태스크: [어떤 유형의 작업을 등록/요청하는지]

## 재호출 지침
- 이전 산출물이 존재하면 읽고 개선점을 반영한다
- 사용자 피드백이 주어지면 해당 부분만 수정한다

## 에러 핸들링
- [실패 시 행동]
- [입력 누락/모호 시 행동]

## 협업
- 다른 에이전트와의 관계
```

**워크플로우 모드 전용 에이전트:** 통신 프로토콜 섹션 대신 "구조화 출력" 섹션을 넣는다 — 반환할 JSON shape을 명시하고, 최종 텍스트가 사람용 메시지가 아니라 **반환 데이터**임을 기재한다.

## 6. 에이전트 분리 기준

| 기준 | 분리 | 통합 |
|------|------|------|
| 전문성 | 영역이 다르면 분리 | 영역이 겹치면 통합 |
| 병렬성 | 독립 실행 가능하면 분리 | 순차 종속이면 통합 고려 |
| 컨텍스트 | 컨텍스트 부담이 크면 분리 | 가볍고 빠르면 통합 |
| 재사용성 | 다른 팀에서도 쓰면 분리 | 이 팀에서만 쓰면 통합 고려 |

## 7. 스킬 vs 에이전트 구분

| 구분 | 스킬 (Skill) | 에이전트 (Agent) |
|------|-------------|-----------------|
| 정의 | 절차적 지식 + 도구 번들 | 전문가 페르소나 + 행동 원칙 |
| 위치 | `.claude/skills/` | `.claude/agents/` |
| 트리거 | 사용자 요청 키워드 매칭 (description) | Agent/Workflow 도구로 명시적 호출 |
| 용도 | "어떻게 하는가" | "누가 하는가" |

### 스킬 ↔ 에이전트 연결 방식

| 방식 | 구현 | 적합한 경우 |
|------|------|-----------|
| **Skill 도구 호출** | 에이전트 프롬프트에 `Skill 도구로 /skill-name 호출` 명시 | 스킬이 독립 워크플로우이고 사용자 호출도 가능한 경우 |
| **프롬프트 내 인라인** | 에이전트 정의 내에 스킬 내용을 직접 포함 | 스킬이 짧고(50줄 이하) 이 에이전트 전용인 경우 |
| **레퍼런스 로드** | `Read`로 스킬의 references/ 파일을 필요 시 로드 | 스킬 내용이 크고 조건부로만 필요한 경우 |

권장: 재사용성이 높으면 Skill 도구, 전용이면 인라인, 대용량이면 레퍼런스 로드.
