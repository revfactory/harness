# 오케스트레이터 스킬 템플릿 (v2)

오케스트레이터는 팀 전체를 조율하는 상위 스킬이다. 실행 모드별로 3가지 템플릿을 제공한다:

- **템플릿 A: 워크플로우 오케스트레이션** — 결정적 제어 흐름 (팬아웃/검증 루프/대규모)
- **템플릿 B: 퍼시스턴트 에이전트 협업** — 반복 피드백·협상·장기 전문가
- **템플릿 C: 서브에이전트 위임** — 단발 병렬, 결과만 수집
- **하이브리드** — Phase마다 모드를 섞는 구성

공통 원칙: 모든 템플릿은 Phase 0(컨텍스트 확인)을 포함하고, `_workspace/` 컨벤션과 에러 핸들링, 테스트 시나리오를 갖춘다.

---

## 템플릿 A: 워크플로우 오케스트레이션

```markdown
---
name: {domain}-orchestrator
description: "{도메인} 워크플로우를 조율하는 오케스트레이터. {초기 실행 키워드}. 후속 작업: {도메인} 결과 수정, 부분 재실행, 업데이트, 보완, 다시 실행, 이전 결과 개선 요청 시에도 반드시 이 스킬을 사용."
---

# {Domain} Orchestrator

## 실행 모드: 워크플로우 오케스트레이션

이 스킬은 Workflow 도구로 결정적 오케스트레이션을 수행한다. 사용자가 이 스킬을 트리거한 것이
Workflow 옵트인에 해당한다. 기본 규모는 {N}개 에이전트로 절제하고, 사용자가 "철저히/전수/모두"를
요청한 경우에만 확장한다.

## 에이전트 구성

| 역할 | agentType | 스킬 | 산출 (schema 요약) |
|------|-----------|------|--------------------|
| {collector} | {커스텀 또는 기본} | {skill} | {findings: [...]} |
| {verifier}  | {커스텀 또는 기본} | {skill} | {refuted, reason} |

## 워크플로우

### Phase 0: 컨텍스트 확인 (후속 작업 지원)

1. `_workspace/` 존재 여부 확인:
   - 미존재 → 초기 실행
   - 존재 + 부분 수정 요청 → 부분 재실행
   - 존재 + 새 입력 → 기존 `_workspace/`를 `_workspace_{ts}/`로 이동 후 새 실행
2. 부분 재실행이고 직전 실행의 runId가 `_workspace/run_meta.json`에 있으면:
   - 스크립트의 해당 단계만 수정 후 `resumeFromRunId`로 재개 — 변경 없는 agent() 호출은
     캐시에서 즉시 반환되므로 저렴하다
3. 새 실행이면 runId를 새로 받아 `_workspace/run_meta.json`에 기록

### Phase 1: 정찰 (인라인)

워크플로우 시작 전에 작업 목록을 확정한다 — {파일 목록 / 조사 축 / 검토 대상}을
가볍게 탐색하여 배열로 정리. 이 목록을 `args`로 스크립트에 주입한다.

### Phase 2: 워크플로우 실행

Workflow 도구를 다음 스크립트로 호출한다 (레시피 상세: harness 스킬의 workflow-recipes.md):

- meta: name '{domain}-run', phases [{수집}, {검증}, {종합}]
- 수집: pipeline(args.items, item => agent(..., {schema: COLLECT}))
- 검증: 발견별 적대적 검증 → .filter(Boolean) → 생존만 통과
- 종합: 구조화 결과 return

호출 후 완료 알림을 대기한다 (결과를 예단하지 않는다).

### Phase 3: 종합 보고

1. 워크플로우 반환값을 수신
2. 드랍/누락된 항목이 있으면 보고서에 명시 (침묵 절단 금지)
3. 최종 산출물 생성: `{output-path}/{filename}`
4. `_workspace/`에 중간 산출물과 run_meta.json 보존

## 에러 핸들링

| 상황 | 전략 |
|------|------|
| agent() 개별 실패 (null 반환) | filter(Boolean)로 제외하고 드랍 수 log(), 보고서에 누락 명시 |
| 워크플로우 전체 실패 | journal에서 실제 반환값 확인 후, 실패 단계만 수정하여 resumeFromRunId로 재개 |
| 결과가 비어 있음 | 성공으로 오독 금지 — journal에서 각 에이전트의 실제 반환값 확인 |
| 상충 데이터 | 삭제하지 않고 출처 병기 |

## 테스트 시나리오

### 정상 흐름
1. 사용자가 {입력} 제공 → 정찰로 {M}개 항목 확정
2. 워크플로우 실행: 수집 {M}건 → 검증 통과 {K}건 → 종합
3. 예상 결과: `{output-path}/{filename}` 생성, run_meta.json 기록

### 에러 흐름
1. 수집 단계에서 항목 2건이 null 반환
2. filter(Boolean) 후 진행, log로 "2건 드랍" 통지
3. 최종 보고서에 "{항목명} 2건 수집 실패" 명시
```

# {Domain} Orchestrator

## 실행 모드: 퍼시스턴트 에이전트 협업

세션의 단일 암묵 팀 위에서 이름 붙인 에이전트들을 조율한다.
팀 생성/해체 절차는 없다 — TeamCreate/TeamDelete는 존재하지 않는 v1 유물이다.

## 에이전트 구성

| 이름 | subagent_type | 역할 | 스킬 | 출력 |
|------|--------------|------|------|------|
| {teammate-1} | {커스텀 또는 빌트인} | {역할} | {skill} | {output-file} |
| {teammate-2} | {커스텀 또는 빌트인} | {역할} | {skill} | {output-file} |

## 워크플로우

### Phase 0: 컨텍스트 확인
(템플릿 A와 동일 — `_workspace/` 존재 여부로 초기/부분/새 실행 분기.
부분 재실행 시 이전 산출물 경로를 에이전트 프롬프트에 포함해 기존 결과를 읽고 반영하게 한다.)

### Phase 1: 준비
1. 사용자 입력 분석 — {무엇을 파악하는지}
2. `_workspace/` 생성, 입력을 `_workspace/00_input/`에 저장

### Phase 2: 에이전트 스폰 + 작업 등록

1. 단일 메시지에서 병렬 스폰 (name 필수 — SendMessage 주소가 된다):
   - Agent(name: "{teammate-1}", subagent_type: "{type}", prompt: "{역할 + 작업 지시 + 산출 경로}")
   - Agent(name: "{teammate-2}", subagent_type: "{type}", prompt: "...")
2. 공유 작업 목록 등록:
   - TaskCreate({title: "{작업1}", assignee: "{teammate-1}"})
   - TaskCreate({title: "{작업3}", depends_on: [작업1]})
   > 팀원당 3~6개 작업이 적정. 의존 작업은 depends_on으로 명시.

### Phase 3: 협업 조율

- 팀원 완료/유휴 알림을 수신하며 진행. 전체 진행률은 TaskList로 확인
- 피드백 루프: SendMessage({to: "{teammate-2}"}, "{teammate-1}의 _workspace/01_... 초안을
  검토하고 수정 지시를 회신하라") → 회신을 {teammate-1}에게 전달 → 수정
  (에이전트가 컨텍스트를 유지하므로 "아까 그 초안의 2절만"이 통한다)
- 팀원 간 직접 협의가 필요한 발견은 리더가 중계하되, 산출물은 항상 파일로 남긴다

**산출물 저장:**
| 팀원 | 출력 경로 |
|------|----------|
| {teammate-1} | `_workspace/{phase}_{teammate-1}_{artifact}.md` |
| {teammate-2} | `_workspace/{phase}_{teammate-2}_{artifact}.md` |

### Phase 4: 통합
1. 태스크 전체 완료 확인 (TaskList)
2. 각 산출물을 Read로 수집 → {통합/검증 로직}
3. 최종 산출물 생성: `{output-path}/{filename}`

### Phase 5: 마무리
1. `_workspace/` 보존 (사후 검증·감사 추적용)
2. 사용자에게 결과 요약 보고
   (팀 해체 절차는 없다 — 에이전트는 작업 완료 후 자연 종료, 필요 시 TaskStop)

## 에러 핸들링

| 상황 | 전략 |
|------|------|
| 팀원 무응답/중지 | SendMessage로 상태 확인 → 재지시 → 실패 시 새 이름으로 대체 스폰 |
| 팀원 과반 실패 | 사용자에게 알리고 진행 여부 확인 |
| 타임아웃 | 수집된 부분 결과로 진행, 미완료 영역을 보고서에 명시 |
| 데이터 충돌 | 출처 명시 후 병기, 삭제 금지 |
| 태스크 상태 지연 | TaskList 확인 후 수동 TaskUpdate |

## 테스트 시나리오

### 정상 흐름
1. {입력} 제공 → Phase 2에서 {N}명 스폰 + {M}개 작업 등록
2. Phase 3 피드백 루프 {K}회 → Phase 4 통합
3. 예상 결과: `{output-path}/{filename}` 생성

### 에러 흐름
1. Phase 3에서 {teammate-2} 무응답
2. SendMessage 상태 확인 → 재지시 실패 → "{teammate-2}b"로 대체 스폰, 기존 산출물 경로 인계
3. 최종 보고서에 "{teammate-2} 영역 일부 재작업" 명시
```

## 실행 모드: 서브에이전트 위임

## 워크플로우

### Phase 0: 컨텍스트 확인
(공통 — `_workspace/` 분기)

### Phase 1: 준비
입력 분석, `_workspace/` 생성

### Phase 2: 병렬 실행
단일 메시지에서 N개 Agent 도구를 동시 호출 (기본 백그라운드):

| 에이전트 | subagent_type | 입력 | 출력 |
|---------|--------------|------|------|
| {agent-1} | {타입} | {소스} | `_workspace/{phase}_{agent}_{artifact}.md` |
| {agent-2} | {타입} | {소스} | `_workspace/{phase}_{agent}_{artifact}.md` |

완료 알림을 대기한다. 위임한 검색을 메인이 중복 수행하지 않는다.

### Phase 3: 통합
1. 반환값 + 파일 산출물 수집 → 통합 로직 → 최종 산출물

### Phase 4: 마무리
`_workspace/` 보존, 결과 요약 보고

## 에러 핸들링
- 에이전트 1개 실패: 1회 재시도. 재실패 시 누락 명시하고 진행
- 과반 실패: 사용자에게 알리고 진행 여부 확인
```

## 하이브리드 구성

Phase마다 다른 실행 모드를 사용한다. 각 Phase 상단에 `**실행 모드:**`를 명시한다.

```markdown
## 실행 모드: 하이브리드

| Phase | 모드 | 이유 |
|-------|------|------|
| Phase 1 (정찰) | 인라인/서브 | 작업 목록 확정 |
| Phase 2 (대량 수집+검증) | 워크플로우 | 결정적 팬아웃 + 적대적 검증 |
| Phase 3 (합의 통합) | 퍼시스턴트 | 상충 데이터 토론·합의 필요 |
| Phase 4 (독립 검증) | 서브에이전트 | QA 1명이 객관 검증 |
```

**하이브리드 전환 규칙:**
- 워크플로우 → 퍼시스턴트: 워크플로우의 구조화 반환값을 파일(`_workspace/`)로 저장한 뒤, 퍼시스턴트 에이전트 프롬프트에 경로로 전달
- 퍼시스턴트 → 워크플로우: 팀 산출물 파일 경로 목록을 `args`로 스크립트에 주입
- 모드 전환 지점마다 데이터 전달 경로를 명시 (dead link 금지)

## 작성 원칙 (전 템플릿 공통)

1. **실행 모드를 최상단에 명시** — 하이브리드면 Phase별 모드 표 필수
2. **워크플로우 모드는 스크립트 구조를 구체적으로** — phases, schema 요약, args 주입 목록
3. **퍼시스턴트 모드는 name/SendMessage/Task 사용법을 구체적으로** — 스폰 목록, 통신 규칙, 의존성
4. **서브 모드는 Agent 파라미터를 완전히 명시** — name 없이(단발) / subagent_type / prompt / 출력 경로
5. **파일 경로는 명확하게** — `_workspace/` 기준 경로, `{phase}_{agent}_{artifact}.{ext}` 컨벤션
6. **Phase 간 의존성 명시** — 모드 전환 지점은 특히 강조
7. **에러 핸들링은 현실적으로** — "모든 것이 성공한다"고 가정하지 않음
8. **테스트 시나리오 필수** — 정상 1 + 에러 1 이상
9. **v1 유물 금지** — TeamCreate/TeamDelete/team_name/브로드캐스트/실험 플래그 참조가 있으면 잘못 생성된 것

## description 작성 시 후속 작업 키워드

- 재실행/다시 실행/업데이트/수정/보완
- "{도메인}의 {부분}만 다시"
- "이전 결과 기반으로", "결과 개선"
- 도메인 관련 일상적 요청 (예: 런치 전략 하네스라면 "런치", "홍보", "트렌딩")

후속 키워드가 없으면 첫 실행 후 하네스가 사실상 죽은 코드가 된다.
