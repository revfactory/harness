# Claude 모델 선택 가이드

에이전트 정의 시 모델은 업무의 **복잡도 · 작업 기간 · 자율성 · 응답 속도** 4가지 기준으로 선택한다. 지정 위치는 에이전트 프론트매터 `model:`, Agent 도구의 `model` 파라미터, Workflow `agent()`의 `opts.model` 세 곳이며, 선택 근거는 에이전트 정의 또는 오케스트레이터에 주석으로 남긴다.

## 요약 결정표

| 티어 | 한 줄 정의 | 대표 업무 |
|------|----------|----------|
| **opus** | 복잡한 문제를 깊이 분석하고, 스스로 계획을 세워 여러 단계를 연결해 최종 결과물까지 만드는 최상위 추론·자율 실행 모델 | 설계·아키텍처, 코드 생성, 복잡한 분석, 교차 검증, 창작, 에이전트 오케스트레이션, 계획 수립과 장기적인 실행 |
| **sonnet** | 글쓰기, 코딩, 분석, 조사 등 대부분의 일상 업무를 균형 있게 처리하는 범용 모델 | 로그 파싱, 포맷 변환, 정적 파일 검사, 배포 스크립트 실행, 단순 수집 |

## 1. Opus

**핵심 역할:** 어려운 문제를 깊이 있게 분석하고 해결하는 고성능 추론 모델. 특정 문제를 깊이 파고들어 논리적으로 분석하는 것은 물론, 목표를 이해한 뒤 여러 단계를 계획하고 연결하여 최종 결과물을 만드는 장기·자율 실행까지 담당한다.

### 적합한 업무

**① 복잡한 조사와 분석** — 단순히 정보를 찾는 것이 아니라, 여러 근거를 평가하고 논리적인 결론을 도출해야 하는 업무.
- 복잡한 산업이나 시장에 대한 심층 조사
- 여러 연구 결과의 비교 분석
- 정책이나 사업 전략의 장단점 평가
- 데이터와 문서를 바탕으로 원인과 결과 분석
- 서로 다른 관점을 종합한 결론 작성

**② 긴 기술 문서 처리** — 전문 용어와 복잡한 구조를 포함한 긴 문서를 읽고 이해하는 작업. 소프트웨어 설계 문서, 시스템 아키텍처 문서, 연구 논문, 기술 규격서, 제품 요구사항 문서, 복잡한 API/개발 문서. 문서를 짧게 줄이는 것보다 **논리 구조와 기술적 의미를 파악**하는 작업에 적합하다.

**③ 연구 방법론 비판** — 연구 결과만 보는 것이 아니라, 그 결과가 만들어진 방식이 타당한지 검토하는 업무.
- 연구 설계가 적절한지, 표본이 충분하고 편향되지 않았는지
- 측정 방식과 통계적 결론에 문제가 없는지
- 결론이 실제 근거보다 과장되지 않았는지, 다른 해석 가능성은 없는지

**④ 에이전트형 코딩** — 코드 한두 줄 생성이 아니라, 목표를 이해하고 여러 개발 작업을 연속적으로 수행하는 코딩 업무.
- 기존 코드베이스 분석, 오류 원인 탐색
- 여러 파일에 걸친 코드 수정, 기능 구현과 테스트 작성
- 코드 구조 개선, 개발 과정에서 다음 단계를 판단하며 작업

**⑤ 여러 단계가 연결된 장기 업무** — 한 번의 답변으로 끝나지 않고 여러 작업을 순서대로 수행해야 하는 경우.
- 시장 조사 → 경쟁사 분석 → 전략 수립 → 보고서 작성
- 요구사항 분석 → 서비스 구조 설계 → 개발 계획 작성 → 결과물 제작
- 여러 문서를 검토한 뒤 통합된 결론과 실행 계획 도출
- 장기간 진행되는 프로젝트의 전체 과정 설계

핵심은 개별 단계가 독립되어 있지 않고, **앞 단계의 결과가 다음 단계에 영향을 주는** 작업이라는 점이다.

**⑥ 방대하고 밀도 높은 자료 처리** — 논문, 보고서, 회의록, 기술 문서처럼 내용이 많고 복잡한 자료를 함께 검토해야 할 때. 단순 요약이 아니라 다음과 같은 고난도 처리가 필요한 상황:
- 여러 자료 사이의 공통점과 차이점 분석
- 서로 충돌하는 주장 확인
- 핵심 근거와 주변 정보를 구분
- 많은 자료를 하나의 논리적인 결과물로 통합

**⑦ 막연한 아이디어를 실제 결과물로 만들기** — 완성된 요구사항 없이 대략적인 아이디어만 주어졌을 때, 필요한 세부 요소를 스스로 구체화하는 업무.
- "이런 느낌의 서비스"라는 아이디어를 사업 기획서로 발전
- 대략적인 주제만 보고 발표 자료의 구조와 내용을 설계
- 불완전한 제품 아이디어를 기능 목록과 개발 계획으로 구체화
- 초안이 없는 상태에서 완성된 보고서나 콘텐츠 제작

즉, 지시를 그대로 실행하는 것보다 **빈 부분을 판단하고 채우는 능력**이 중요할 때 선택한다.

### 선택하기 좋은 상황

- 문제 자체가 전문적이고 어려운 경우
- 깊은 논리적 분석과 검토가 필요한 경우
- 기술 문서나 논문을 정확히 이해해야 하는 경우
- 연구나 분석의 허점을 찾아야 하는 경우
- 복잡한 코딩 또는 기술적 문제 해결이 필요한 경우
- 결과를 얻기까지 여러 단계가 필요하고, 모델이 스스로 작업 순서를 계획해야 하는 경우
- 방대한 자료를 바탕으로 프로젝트 단위의 완성된 결과물을 만들어야 하는 경우

## 2. Sonnet

**핵심 역할:** 대부분의 일반적인 업무를 처리할 수 있는 균형 잡힌 범용 모델. 최고 수준의 복잡성과 전문성을 전제로 하지 않지만, 글쓰기부터 코딩, 조사, 분석까지 폭넓게 사용한다.

### 적합한 업무

**① 글쓰기와 콘텐츠 제작** — 이메일, 블로그 글, 보고서 초안, 광고 문구, 문장 교정·재작성, 발표 원고, SNS 콘텐츠 기획, 브레인스토밍.

**② 일반적인 코딩 업무** — 함수 작성, 코드 오류 수정, 간단한 프로그램 개발, 기존 코드 설명, 리팩터링, 테스트 코드 작성, 데이터 처리 스크립트.

**③ 분석과 조사** — 주제 개요 정리, 제품·서비스 비교, 문서 내용 분석, 간단한 경쟁사 조사, 핵심 주장 추출, 장단점 비교, 결과를 표나 보고서로 구성.

**④ 다단계 문제 해결** — 범위가 명확한 다단계 업무. 자료 요약 후 발표문 작성, 요구사항 분석 후 코드 예시 작성, 데이터 분석 후 결과 설명. (Opus가 담당하는 장기·자율 프로젝트와 구분된다.)

**⑤ 기계적·운영성 업무** — 로그 파싱, 포맷 변환, 정적 파일 검사, 배포 스크립트 실행, 단순 수집.

### 선택하기 좋은 상황

- **어떤 모델을 선택해야 할지 확실하지 않은 경우** (애매하면 sonnet이 기본값)
- 일상적인 업무를 빠르고 안정적으로 처리하려는 경우
- 글쓰기, 코딩, 조사 등 여러 종류의 작업을 함께 수행하는 경우
- 너무 단순하지도, 지나치게 복잡하지도 않은 문제
- 속도와 결과 품질 사이의 균형이 중요한 경우

## Opus vs Sonnet 구분 기준

- **Opus**: 깊은 추론이 필요하거나, 전체 작업을 계획하고 장기간 자율적으로 수행해야 하는 업무
- **Sonnet**: 절차와 범위가 명확하고, 속도-품질 균형이 중요한 일상 업무

예: 하나의 논문을 깊게 비판하거나 수십 개의 논문을 검토해 연구 전략과 최종 보고서까지 만드는 업무는 **Opus**, 회의록 하나를 요약해 정해진 양식의 표로 정리하는 업무는 **Sonnet**. 판단의 여지가 크고 앞 단계 결과가 다음 단계를 바꾸면 Opus, 절차가 정해져 있고 실행만 남았으면 Sonnet.

## 하네스 적용 규칙

1. **업무 단위로 판단한다** — "이 에이전트가 중요하니까"가 아니라, 에이전트가 담당하는 업무의 성격(복잡도·기간·자율성·속도)으로 티어를 정한다.
2. **무근거 일괄 지정 금지** — "전부 opus" 같은 일괄 지정은 비용만 늘리고 근거를 남기지 않는다. 에이전트별로 판단하고 이유를 주석으로 남긴다.
3. **계층 분리** — 계획·조율을 담당하는 오케스트레이션 계층(메인 세션 또는 감독자 에이전트)에 opus를 두었다면, 그 아래 워커들은 각자의 업무 특성에 맞는 티어를 따로 적용한다. 오케스트레이터가 opus라고 워커까지 opus일 필요는 없다.
4. **워크플로우 단계별 적용** — Workflow 스크립트에서는 `opts.model`로 단계마다 다르게 지정할 수 있다. 기계적 수집 단계는 sonnet, 심층 검증·심판·종합 설계 단계는 opus.
