## 1. 모드 A: 워크플로우 오케스트레이션

`Workflow` 도구로 결정적 오케스트레이션 스크립트를 실행한다. 제어 흐름(팬아웃, 루프, 조건 분기)을 모델 판단이 아니라 **코드**로 고정하므로, 재현성이 높고 대규모 병렬에 강하다.

```
[메인] → Workflow(script)
           ├── phase('Find'):   pipeline(items, item => agent(...))
           ├── phase('Verify'): 발견별 적대적 검증 (병렬)
           └── return { confirmed }   ← 구조화된 최종 결과
```

**핵심 프리미티브:**
- `agent(prompt, opts)` — 서브에이전트 스폰. `opts.schema`(JSON Schema)를 주면 **검증된 구조화 객체**를 반환 (파싱 불필요, 불일치 시 자동 재시도). `opts.agentType`으로 `.claude/agents/`의 커스텀 에이전트 사용. `opts.effort`로 추론 강도 조절, `opts.isolation: 'worktree'`로 파일 변경 격리
- `pipeline(items, stage1, stage2, ...)` — 항목별 독립 진행, 단계 간 배리어 없음. **다단계 작업의 기본값**
- `parallel(thunks)` — 배리어. 이후 단계가 이전 단계 **전체** 결과를 필요로 할 때만 (dedup, 전체 카운트 기반 조기 종료 등)
- `phase(title)` / `log(msg)` — 진행 그룹핑과 사용자용 진행 메시지
- `budget` — 사용자의 토큰 버짓 지시("+500k")에 연동. `budget.total`/`budget.remaining()`으로 규모를 동적 조절
- `workflow(nameOrRef, args)` — 다른 워크플로우를 1단계까지 중첩 실행 (계층적 위임에 활용)

**특징:**
- 제어 흐름이 결정적 — 같은 입력이면 같은 구조로 실행
- 구조화 출력(schema)으로 단계 간 데이터가 타입 안전하게 흐름
- `resumeFromRunId`로 재개 — 변경 없는 `agent()` 호출은 캐시에서 즉시 반환 (부분 재실행이 저렴)
- 백그라운드 실행 — 완료 시 알림 수신

**제약:**
- **사용자 옵트인 필수.** 사용자가 워크플로우/멀티에이전트 오케스트레이션을 직접 요청했거나, Workflow 호출을 지시하는 스킬을 사용자가 트리거한 경우에만 호출 가능. 하네스가 생성한 오케스트레이터 스킬은 후자에 해당한다 — 단, 기본 규모는 절제하고 대규모 팬아웃은 사용자가 명시적으로 요청했을 때만
- 스크립트는 순수 JavaScript (TypeScript 문법 불가). `Date.now()`/`Math.random()`/인자 없는 `new Date()`는 사용 불가 (resume을 깨뜨림) — 타임스탬프는 `args`로 주입
- `meta` 블록은 순수 리터럴 (변수/함수 호출/스프레드 금지)
- 동시 실행은 세션당 상한이 있고 초과분은 자동 큐잉. 워크플로우 수명 총 에이전트 수 상한 존재 (폭주 방지)
- 실패/스킵된 `agent()`는 `null` 반환, `parallel()`은 절대 reject되지 않음 — 결과에 `.filter(Boolean)` 필수

**적합:** 목록 기반 팬아웃(파일 N개, 관점 M개), 검증 루프(적대적 검증, loop-until-dry), 대규모 마이그레이션/감사, 구조화 보고서 생성
**부적합:** 작업 목록을 사전에 알 수 없고 대화하며 발견해야 하는 작업, 사용자와의 중간 상호작용이 잦은 작업

> 구체적 스크립트 스켈레톤과 함정 목록은 `workflow-recipes.md` 참조.

## 2. 모드 B: 퍼시스턴트 에이전트 협업

이름 붙인 에이전트들을 스폰하고, 공유 태스크 목록과 SendMessage로 조율한다. v1의 "에이전트 팀" 모드를 대체한다.

**v1과의 결정적 차이:** `TeamCreate`/`TeamDelete`는 더 이상 존재하지 않는다. 세션에는 **단일 암묵 팀**이 있으며, 팀 생성·해체 절차 없이 에이전트를 스폰하면 그 팀에 속한다.

```
[메인/리더]
    ├── Agent(name: "researcher", subagent_type: "...", prompt: ...)   ← 병렬 스폰
    ├── Agent(name: "critic", ...)
    ├── TaskCreate(작업 + 의존성) → 공유 태스크 목록
    ├── SendMessage({to: "researcher"}, ...)  ← 컨텍스트 유지한 채 추가 지시
    └── 완료 알림 수신 → 결과 수집 → 종합
```

**핵심 프리미티브:**
- `Agent(prompt, {name, subagent_type, model?})` — `name`을 주면 SendMessage로 주소 지정 가능한 퍼시스턴트 에이전트가 된다. 기본 백그라운드 실행이며 완료 시 알림 수신. 동기 실행이 필요하면 `run_in_background: false`
- `SendMessage({to: name})` — 이전에 스폰한 에이전트를 **컨텍스트를 유지한 채** 이어서 구동. 반복 피드백 루프의 핵심
- `TaskCreate`/`TaskUpdate`/`TaskList`/`TaskGet` — 공유 작업 목록. 의존 관계와 진행 상태 관리, 감독자 패턴의 동적 할당에 활용
- `TaskStop` — 폭주하거나 불필요해진 백그라운드 작업 중지

**특징:**
- 에이전트가 대화 컨텍스트를 축적 — "지난번 그 초안에서 2절만 고쳐줘"가 통한다
- 에이전트 간 발견 공유·상충 토론·실시간 방향 수정 가능
- 세션이 살아있는 동안 전문가를 계속 재사용

**제약:**
- 조율을 메인(리더)이 담당하므로 팀원이 많으면 리더가 병목 — 3~5명 권장
- 깊은 중첩 위임은 지연과 컨텍스트 손실이 크다 — 2단계 이내 권장
- 토큰 비용이 서브에이전트 단발 호출보다 높음

**적합:** 생성자↔검증자 반복 루프, 합의 기반 통합(상충 데이터 토론), 감독자 + 동적 작업 할당, 세션 전체에 걸친 전문가 유지
**부적합:** 결과만 필요한 단발 작업 (오버헤드), 사전 열거 가능한 대규모 팬아웃 (워크플로우가 우월)

## 3. 모드 C: 서브에이전트 위임

`Agent` 도구 단발 호출. 결과만 메인에 반환되고 통신은 없다.

```
[메인] → Agent(서브A) ─┐
       → Agent(서브B) ─┼→ (병렬, 기본 백그라운드) → 완료 알림 → 결과 수집
       → Agent(서브C) ─┘
```

**특징:**
- 가볍고 빠름. 결과가 메인 컨텍스트로 요약 반환
- 독립 호출은 **단일 메시지에 묶어** 보내면 동시 실행된다
- 기본이 백그라운드 실행 — 결과가 즉시 필요하면 `run_in_background: false`
- 위임한 검색을 메인이 중복 수행하지 않는다 — 결과를 기다린다

**제약:**
- 에이전트 간 통신 불가, 컨텍스트 미유지 (같은 이름으로 다시 불러도 새로 시작하려면 name 없이 호출)
- 메인이 모든 조율 담당

**적합:** 단발 조사/수집, 결과 전달만 필요한 전문가 풀 라우팅, 독립 검증 1회
**부적합:** 반복 피드백이 필요한 작업, 대규모 결정적 팬아웃

## 4. 모드 선택 의사결정 트리

```
작업 목록·검증 기준·반복 조건을 사전에 코드로 표현할 수 있는가?
├── Yes → 워크플로우 오케스트레이션 (모드 A)
│         결정적 제어 흐름을 모델 판단에 맡기지 않는다.
│         단, 옵트인 조건과 규모 절제 원칙을 지킨다.
│
└── No → 에이전트 간 반복 피드백·협상·컨텍스트 유지가 품질을 좌우하는가?
          ├── Yes → 퍼시스턴트 에이전트 협업 (모드 B)
          │
          └── No → 에이전트가 2개 이상인가?
                    ├── Yes → 서브에이전트 병렬 위임 (모드 C)
                    └── No  → 서브에이전트 단일 호출 (모드 C)
```

**하이브리드 판단:** Phase별로 위 질문의 답이 달라지면 하이브리드다. 자주 쓰는 조합:

| 조합 | 구성 | 예시 |
|------|------|------|
| 워크플로우 수집 → 퍼시스턴트 통합 | A → B | 대량 자료 팬아웃 수집 후, 상충 데이터를 팀 토론으로 합의 |
| 퍼시스턴트 생성 → 워크플로우 검증 | B → A | 팀이 초안 생성 후, 발견별 적대적 검증 팬아웃 |
| 서브 정찰 → 워크플로우 본대 | C → A | 인라인/서브로 작업 목록 발견(정찰) 후, 목록을 args로 워크플로우에 전달 |

**정찰 후 오케스트레이션 원칙:** 워크플로우를 시작하기 전에 작업 목록(파일 목록, 검토 대상, 조사 축)을 가볍게 정찰하여 확정하라. 오케스트레이션 단계 전에 형태를 알면 스크립트가 단순해지고 낭비가 사라진다.

## 5. v1 → v2 마이그레이션

기존 v1 하네스 산출물(오케스트레이터/에이전트 정의)을 발견하면 아래 매핑으로 변환을 제안한다.

| v1 요소 | 상태 | v2 대체 |
|---------|------|---------|
| `TeamCreate(team_name, members)` | **제거됨** | 단일 메시지에서 `Agent(name: ...)` 병렬 스폰. 팀 생성 절차 자체가 불필요 (단일 암묵 팀) |
| `TeamDelete` / "팀 정리" Phase | **제거됨** | 삭제. 에이전트는 작업 완료 후 자연 종료, 필요 시 `TaskStop` |
| "세션당 한 팀만 활성화" 제약 | **소멸** | 제약 없음 — 이름 붙인 에이전트를 필요한 만큼 스폰 |
| `SendMessage({to: "all"})` 브로드캐스트 | 변경 | 명시적 개별 SendMessage로 대체 (필요한 상대에게만) |
| `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` | **불필요** | 삭제. 문서·스크립트에서 모두 제거 |
| `model: "opus"` 전 에이전트 강제 | 정책 폐기 | 오버라이드 생략(상속)이 기본. 근거 있을 때만 지정 |
| 대규모 팬아웃을 팀으로 구성 | 개선 | `Workflow` 스크립트로 이관 — 결정적 제어 + 구조화 출력 + resume |
| 오케스트레이터 "Phase 0: 컨텍스트 확인" | 유지 | 동일 + 워크플로우 모드는 `resumeFromRunId` 옵션 추가 |
| `_workspace/` 파일 컨벤션 | 유지 | 동일 |
| CLAUDE.md 포인터 + 변경 이력 | 유지 | 동일 |

**마이그레이션 절차:**
1. 기존 오케스트레이터에서 `TeamCreate`/`TeamDelete`/브로드캐스트/실험 플래그 참조를 제거
2. 팬아웃·검증 루프 구간을 식별하여 워크플로우 모드 전환을 검토 (결정적이면 전환)
3. 나머지 협업 구간은 퍼시스턴트 모드 문법(`Agent(name:)` + SendMessage + Tasks)으로 재작성
4. 에이전트 정의에서 `model: "opus"` 일괄 지정을 제거 (근거 있는 것만 유지)
5. Phase 6 검증(구조 + 드라이런)을 재수행하고 CLAUDE.md 변경 이력에 기록
