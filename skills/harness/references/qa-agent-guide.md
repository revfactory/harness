## 1. QA 에이전트가 놓치는 결함의 패턴

### 1-1. 구성 요소 연결부의 계약 불일치(Boundary Mismatch)

가장 자주 발생하는 결함이다. 두 구성 요소를 따로 보면 모두 올바르게 구현되어 있지만, 연결 지점에서 서로 다른 계약을 따르는 경우다.

| 연결 지점 | 불일치 예시 | 놓치는 이유 |
|--------|-----------|-----------|
| API 응답 → 프런트엔드 훅 | API는 `{ projects: [...] }`를 반환하지만 훅은 `Project[]`를 기대한다. | 각 구성 요소만 따로 검증하고 서로 비교하지 않는다. |
| API 응답 필드명 → 타입 정의 | API는 `thumbnailUrl`(camelCase), 타입은 `thumbnail_url`(snake_case)을 사용한다. | 제네릭으로 타입을 단언하면 컴파일러가 감지하지 못한다. |
| 파일 경로 → 링크 `href` | 페이지는 `/dashboard/create`에 있지만 링크는 `/create`를 가리킨다. | 파일 구조와 `href`를 서로 비교하지 않는다. |
| 상태 전이 맵 → 실제 `status` 갱신 | 맵에는 전이가 정의되어 있지만 코드에는 상태를 바꾸는 처리가 빠져 있다. | 맵이 있는지만 확인하고 실제 갱신 코드를 추적하지 않는다. |
| API 엔드포인트 → 프런트엔드 훅 | API는 있지만 이를 호출하는 훅이 없다. | API 목록과 훅 목록을 일대일로 대조하지 않는다. |
| 즉시 응답 → 비동기 처리 결과 | API는 즉시 `{ status }`를 반환하지만 프런트엔드는 최종 결과 필드에 접근한다. | 즉시 응답과 최종 응답을 구분하지 않고 타입만 확인한다. |

### 1-2. 정적 코드 검토만으로 찾기 어려운 이유

- **제네릭 타입의 한계**: `fetchJson<Project[]>()`처럼 쓰면 실제 응답이 `{ projects: [...] }`여도 컴파일을 통과한다.
- **빌드에 성공해도 정상 동작을 보장할 수 없는 이유**: 타입 단언, `any`, 제네릭을 사용한 코드는 빌드에는 성공해도 실행 중에 실패할 수 있다.
- **API의 존재 여부와 응답 계약은 서로 다른 검증 대상**: “API가 있는가?”를 확인하는 것과 “API 응답이 호출하는 쪽에서 기대하는 값과 일치하는가?”를 확인하는 것은 전혀 다른 일이다.

## 2. 통합 정합성 검증(Integration Coherence Verification)

QA 에이전트에는 구성 요소를 **서로 대조하는 검증**을 반드시 포함해야 한다. 아래 예시는 Next.js를 기준으로 하지만, 이 원칙은 어떤 기술 스택에나 적용된다. 생산자 코드와 소비자 코드를 함께 열어 양쪽의 계약을 비교한다.

### 2-1. API 응답과 프런트엔드 훅 타입 대조

```
1. API 라우트(route)의 응답 직렬화 지점(NextResponse.json() 등)에서 응답 구조를 추출한다.
2. 대응하는 훅이나 클라이언트에서 기대하는 타입(fetchJson<T>의 T 등)을 확인한다.
3. 응답 구조와 T를 비교한다. API가 { data: [...] }를 반환한다면 훅이 .data를 꺼내는지까지 확인한다.
```

특히 페이지네이션으로 감싼 응답을 배열로 잘못 받는 경우, snake_case와 camelCase 사이의 변환이 빠진 경우, 즉시 응답(202)과 최종 응답의 구조가 다른 경우를 확인한다.

### 2-2. 파일 경로와 링크·라우터 경로 대조

```
1. 라우팅 파일 구조에서 URL 패턴을 추출한다. (group)은 제거하고 [param]은 동적 세그먼트로 처리한다.
2. 코드에 있는 모든 href=, router.push(, redirect( 값을 수집한다.
3. 각 링크가 실제로 존재하는 경로와 일치하는지 확인한다.
```

### 2-3. 상태 전이가 빠짐없이 구현되었는지 추적

```
1. 상태 전이 맵에서 허용된 전이 목록을 추출한다.
2. status를 갱신하는 코드를 모두 검색한다.
3. 코드에서 일어나는 전이가 맵에 정의되어 있는지 확인한다. 허용되지 않은 전이가 없어야 한다.
4. 맵에는 있지만 코드에서 실행되지 않는 전이를 찾는다. 쓰이지 않는 전이가 없어야 한다.
5. 특히 중간 상태에서 최종 상태로 넘어가는 처리가 빠졌는지 확인한다.
```

### 2-4. API 엔드포인트와 프런트엔드 훅을 일대일로 대조

```
1. HTTP 메서드별 엔드포인트 목록을 추출한다.
2. 클라이언트의 fetch 호출 URL 목록을 추출한다.
3. 호출되지 않는 엔드포인트가 클라이언트에서 직접 호출하지 않는 관리용 API인지, 호출 코드가 빠진 것인지 판단한다.
```

## 3. QA 에이전트 설계 원칙

### 3-1. 모든 도구를 쓸 수 있는 에이전트 유형을 선택한다

QA 에이전트가 `Explore` 유형이면 파일을 읽는 작업만 할 수 있다. QA를 제대로 수행하려면 `Grep`으로 패턴을 찾고, 스크립트를 실행해 결과를 자동으로 대조하며, 필요하면 코드를 수정할 수 있어야 한다. `general-purpose` 또는 모든 도구를 쓸 수 있는 사용자 정의 유형을 선택하고, 에이전트 정의에 “검증 → 보고 → 수정 요청” 절차를 명시한다.

### 3-2. 체크리스트에는 존재 여부보다 대조 결과를 담는다

| 단순한 체크리스트 | 대조 중심 체크리스트 |
|---------------|---------------|
| API 엔드포인트가 있는가? | API 응답 구조와 대응하는 훅의 타입이 일치하는가? |
| 상태 전이 맵이 정의되어 있는가? | `status`를 갱신하는 모든 코드가 전이 맵과 일치하는가? |
| 페이지 파일이 있는가? | 코드의 모든 링크가 실제로 존재하는 페이지를 가리키는가? |
| 엄격 모드(strict mode)를 사용하는가? | 제네릭 타입 단언으로 타입 안전성을 우회한 곳이 없는가? |

### 3-3. 연결된 양쪽 코드를 함께 읽는다

연결 지점에서 생기는 버그를 찾으려면 한쪽 코드만 읽어서는 안 된다. API 라우트와 대응하는 훅, 상태 전이 맵과 실제 갱신 코드, 파일 구조와 링크 경로를 각각 함께 읽는다. 에이전트 정의에도 이 원칙을 분명하게 적는다.

### 3-4. 모든 모듈을 만든 뒤가 아니라 각 모듈을 완성할 때마다 QA를 실행한다

QA를 전체 구현이 끝난 뒤에만 실행하면 버그가 쌓여 수정 비용이 늘고, 초기에 생긴 계약 불일치가 후속 모듈까지 퍼진다. API 엔드포인트 한 개를 완성할 때마다 해당 API와 대응하는 훅을 곧바로 대조하는 **점진적 QA(incremental QA)**를 권장한다.

## 4. 워크플로로 수행하는 QA(v2)

검증할 연결 지점을 목록으로 만들 수 있다면 QA 과정도 워크플로로 구성할 수 있다.

```javascript
// 연결 지점을 나누어 검사 → 발견한 항목마다 반대 관점에서 재검증
const FINDINGS = { type: 'object', required: ['findings'], properties: {
  findings: { type: 'array', items: { type: 'object',
    required: ['title', 'file', 'evidence'], properties: {
      title: { type: 'string' }, file: { type: 'string' }, evidence: { type: 'string' } } } } } }
const VERDICT = { type: 'object', required: ['status', 'reason'], properties: {
  status: { type: 'string', enum: ['confirmed', 'refuted', 'uncertain'] },
  reason: { type: 'string' } } }
const boundaries = args.boundaries  // 사전 조사로 추출: [{api: '...', consumer: '...'}, ...]
const found = await pipeline(
  boundaries,
  b => agent(`양쪽을 함께 읽고 계약 불일치를 찾아라: ${b.api} ↔ ${b.consumer}`,
    { agentType: 'qa-inspector', phase: '검사', schema: FINDINGS }),
  r => parallel((r?.findings ?? []).map(f => () =>
    agent(`이 불일치가 실제 실행 오류를 일으키는지 반대 관점에서 검증하라: ${JSON.stringify(f)}`,
      { phase: '재검증', schema: VERDICT }).then(verdict => ({ ...f, verdict }))))
)
const confirmed = found.flat().filter(Boolean)
  .filter(f => f.verdict?.status === 'confirmed')
return { confirmed }
```

발견한 항목을 반대 관점에서 다시 검증하고 `confirmed` 판정만 남기면, 그럴듯해 보이지만 실제로는 문제가 아닌 지적을 걸러낼 수 있다. 따라서 최종 QA 보고서에 담긴 지적을 더 신뢰할 수 있다.

## 5. 검증 체크리스트 템플릿

웹 애플리케이션을 검사하는 QA 에이전트 정의에 아래 통합 정합성 체크리스트를 포함한다.

```markdown
### 통합 정합성 검증(웹 앱)

#### API와 프런트엔드 연결
- [ ] 모든 API 라우트의 응답 구조와 대응하는 훅의 제네릭 타입이 일치하는지 확인한다.
- [ ] 훅이 객체로 감싼 응답({ items: [...] })에서 실제 데이터 값을 꺼내는지 확인한다.
- [ ] snake_case와 camelCase 사이의 변환을 일관되게 적용하는지 확인한다.
- [ ] 프런트엔드가 즉시 응답(202)과 최종 응답의 구조를 구분하는지 확인한다.
- [ ] 모든 API 엔드포인트에 대응하는 프런트엔드 훅이 있고 실제로 호출되는지 확인한다.

#### 라우팅 정합성
- [ ] 코드의 모든 href/router.push 값이 실제 페이지 파일 경로와 일치하는지 확인한다.
- [ ] 라우트 그룹(route group)에 쓴 (group)이 URL에서 빠진다는 점을 반영해 경로를 검증한다.
- [ ] 동적 세그먼트([id])에 올바른 매개변수 값이 들어가는지 확인한다.

#### 상태 머신 정합성
- [ ] 정의된 모든 상태 전이가 코드에서 실행되는지 확인한다(쓰이지 않는 전이가 없어야 한다).
- [ ] 코드의 모든 status 갱신이 전이 맵에 정의되어 있는지 확인한다(허용되지 않은 전이가 없어야 한다).
- [ ] 중간 상태에서 최종 상태로 넘어가는 처리가 빠지지 않았는지 확인한다.
- [ ] 프런트엔드의 상태에 따른 분기(if status === "X")에 있는 X가 실제로 도달할 수 있는 상태인지 확인한다.

#### 데이터 흐름 정합성
- [ ] DB 스키마 필드명과 API 응답 필드명의 대응 관계가 일관되는지 확인한다.
- [ ] 프런트엔드 타입 정의와 API 응답의 필드명이 일치하는지 확인한다.
- [ ] 양쪽에서 선택적 필드(optional field)의 null/undefined 값을 일관되게 처리하는지 확인한다.
```

## 6. QA 에이전트 정의 템플릿

```markdown
---
name: qa-inspector
description: "명세 준수 여부와 통합 정합성, 디자인 품질을 검증하는 QA 에이전트다."
---

# QA 에이전트

## 주요 역할
명세대로 구현되었는지 확인하고 **모듈 사이의 통합 정합성**을 검증한다.

## 검증 우선순위
1. **통합 정합성**(가장 높음) — 연결 지점의 계약 불일치는 실행 중 오류를 일으키는 주요 원인이다.
2. **기능 명세 준수** — API, 상태 머신, 데이터 모델을 확인한다.
3. **디자인 품질** — 색상, 글꼴, 반응형 동작을 확인한다.
4. **코드 품질** — 쓰이지 않는 코드와 명명 규칙을 확인한다.

## 검증 방법: 연결된 양쪽 코드를 함께 읽기
| 검증 대상 | 생산자 | 소비자 |
|----------|-------|-------|
| API 응답 구조 | 응답 직렬화 지점 | 클라이언트가 기대하는 타입 |
| 라우팅 | 라우팅 파일 구조 | href, router.push 값 |
| 상태 전이 | 전이 맵 | status 갱신 코드 |
| DB → API → UI | DB 테이블의 열 이름 | API 응답 필드 → 타입 정의 |

## 보고 및 수정 요청 절차
- 문제를 발견하면 담당 에이전트에게 곧바로 구체적인 수정 사항을 요청한다(파일:줄 번호 + 수정 방법).
- 연결 지점에서 문제가 생겼다면 양쪽 담당 에이전트에게 모두 알린다.
- 리더에게는 통과, 실패, 미검증 항목을 구분한 검증 보고서를 보낸다.
```

## 실제 사례: 발견된 버그와 원인

| 버그 | 연결 지점 | 원인 |
|------|----------|------|
| `projects?.filter is not a function` | API → 훅 | API는 `{projects:[]}`를 반환하지만 훅은 배열을 기대한다. |
| 대시보드의 모든 링크에서 404 발생 | 파일 경로 → `href` | `/dashboard/` 접두사가 빠져 있다. |
| 썸네일 이미지가 보이지 않음 | API → UI 구성 요소 | `thumbnailUrl`과 `thumbnail_url`이 일치하지 않는다. |
| 선택한 값이 저장되지 않음 | API → 훅 | API는 있지만 대응하는 훅이 없다. |
| 생성 페이지가 계속 대기 상태에 머묾 | 상태 전이 → 코드 | 최종 상태로 바꾸는 코드가 빠져 있다. |
| `data.failedIndices` 접근 시 크래시 발생 | 즉시 응답 → 프런트엔드 | 프런트엔드가 즉시 응답에서 백그라운드 처리 결과에 접근한다. |
| 완료 뒤 상세 페이지를 열면 404 발생 | 파일 경로 → `href` | 라우트 접두사가 일치하지 않는다. |
